# 多人共用知识库:架构选择与最终设计

前提(来自你的要求):
- 代码是 source of truth。使用者在使用中发现错误,对照代码修正。
- 知识库本身不判断对错,只做机械比对(版本 hash)和冲突标记。
- 形态:中央 server + 本机 user-scope 的 Claude Code skill 与 script。
- 使用者没有负担,没有隐私焦虑,边做边修正。

## 1. 比较了六种架构

人是规则模拟(不是 LLM),100 人、35 个工作日、6 个随机种子,取第 25–35 天均值。代码是合成的 120 个事实(12 模块)。**「人的参数」是我假设的**,所以每个架构跑两遍:
- **照设计**:含各自的人为摩擦(例如 PR 有延迟、自动录制有人拒绝被录)。
- **同样的人**:把回写意愿、拒绝比例都设成一样,只留架构本身的结构差异。

| 架构 | 对应的现有做法 | 关键设定(假设) |
|---|---|---|
| A Git 文件 | CLAUDE.md + PR | PR 延迟 2 天,回写意愿低,reviewer 能挡掉一半错写入,key 不会不一致 |
| B 全自动录制 | Stash、claude-mem | 回写 95%,30% 的人拒绝被录,噪音 ×4,未验证的使用也被再记录(会刷新时间) |
| C 手动存 | Hjarni、Context Cloud | 回写意愿 40% |
| D 原规格 | 你最初定的规格 | 同 key 覆盖、子 key 追加、时间加权、记 source path |
| E 事件回写 + 警示 + 结果回馈 | 我们的设计 | 过期警示、测试失败标记、disputed 保护、检索去时间衰减、核对时与 push 时提示一次 |
| F E + 代码锚定 | 我们的设计加选项 | 60% 的事实能被正则或 AST 从代码机械抽出,CI 自动对齐 |

### 结果

| 架构 | 正确% | 错且没警示% | 漏网 bug / 日 |
|---|---|---|---|
| A Git 文件(照设计) | 86.7 | **12.1** | **7.03** |
| B 全自动录制(照设计) | 86.6 | 6.9 | 3.94 |
| C 手动存(照设计) | 79.1 | 7.9 | 4.79 |
| D 原规格 | 86.9 | 3.9 | 3.27 |
| **E(照设计)** | **95.8** | **0.4** | **1.82** |
| **F(照设计)** | **97.0** | 0.5 | **1.71** |
| E(同样的人) | 92.8 | 0.7 | 2.41 |
| F(同样的人) | 94.9 | 0.4 | 1.68 |
| B(同样的人) | 86.5 | 8.0 | 4.35 |
| A(同样的人) | 88.2 | 10.5 | 6.26 |

读法:
- **E 与 F 排前两名,不管人怎么设**。「同样的人」那一行也成立,代表差距主要来自结构,不是我假设的人。
- **A 最差**。review 把错覆盖压到最低(0.15 次/日),但写入延迟 2 天让别人反复踩到过期内容。**延迟的代价大于审查的好处**。
- **B 没有比手动好多少**。自动录制把没验证过的使用也当确认,刷新了时间,等于把过期的东西伪装成新的;噪音也多。即使没人拒绝被录(0%),也只有 90.6%。
- 漏网 bug 降不到 0。剩下的来自测试抓不到和读码误读。

## 2. 哪些机制有用(拆解)

以 E 为基准(95.8% / 漏网 1.82):

| 拿掉 | 正确% | 错且没警示% | 漏网 | 结论 |
|---|---|---|---|---|
| 检索去时间衰减(改回衰减) | **90.2** | 0.8 | 2.14 | **影响最大**:缺失 1.7% → 6.6% |
| 事件提示(回写靠自觉) | 93.0 | 0.3 | 2.21 | 回写意愿的作用 |
| 结果回馈整组 | 96.0 | **1.6** | 2.00 | 错且没警示变 4 倍 |
| 过期警示 | 96.3 | **1.4** | 1.70 | 错且没警示变 3.5 倍,但读码 −37% |
| 代码锚定 +60% | 97.0 | 0.5 | 1.71 | 用到错答 5.0 → 2.6,读码 −22% |
| 代码锚定 +90% | 97.2 | 0.4 | **1.14** | 漏网 −37% |

重点:
- **过期警示换的是「诚实」,不是准确率**。拿掉它后正确率没降,但错且没警示从 0.4% 升到 1.4%(使用者不知道哪里不可信);代价是每日读码多 10 次(27.9 vs 17.6)。参与度低时更明显:不愿写的人 40% 时,有警示 0.4%、无警示 2.7%。
- **结果回馈**(测试失败标记 + disputed 保护)压低「错且没警示」,对错覆盖则有取舍(两个子机制的数字互相抵消,差异在噪声范围),不要过度解读。
- **代码锚定**是把「读代码核对」自动化:只比对、不判断。它主要降低读码和错答,不是魔法:无法抽取的知识(设计原因)没有帮助,60% 是我设的假设。

## 3. 什么时候提示最划算

都在 E 的基础上,只改提示方式:

| 触发方式 | 正确% | 漏网 / 日 | 读码 / 日 |
|---|---|---|---|
| T0 无提示(靠自觉) | 92.8 | 2.41 | 28.9 |
| **T1 仅 push 时提示(改代码的人)** | **95.1** | **1.73** | 28.4 |
| T2 仅核对时提示 | 94.4 | 2.27 | 28.5 |
| T3 两者都有 | 95.3 | 1.77 | 26.9 |
| **T4 定期提醒(延后 3 天)** | **83.7** | **4.65** | **46.1** |
| T5 两者都有但接受率只有 50% | 91.1 | 2.58 | 32.0 |

- **只在 push 时提醒改代码的人(T1)几乎等于全开(T3)**,是最划算的一个。
- **定期提醒反而最差**:延后让别人反复踩到旧答案。写回要在事件当下,不要排程。
- 接受率只有一半时,效果退回无提示附近。所以提示要少、要准、一键完成。

## 4. 隐私与参与度:没人愿意写会怎样

| 不愿意写/被录的人 | E 正确% | E 漏网 | B 正确% | B 错且没警示% |
|---|---|---|---|---|
| 0% | 95.3 | 1.77 | 90.6 | 4.9 |
| 20% | 95.2 | 2.24 | 88.4 | 6.6 |
| 40% | 92.6 | 2.59 | 86.4 | 7.4 |
| 60% | 88.4 | 3.23 | 82.1 | 9.2 |

- E 容忍 20% 的人不参与几乎没有损失,40% 时少约 3 个百分点;错且没警示一直维持在 0.3–0.5%。
- B 在每一档都比 E 差,而且错且没警示随拒绝比例上升。**设计成「不愿意参与也不会拖垮知识库」,比设法让所有人参与更稳。**

## 5. 压力测试

四种情境(代码变动 ×2、误读 ×2、测试抓漏率 0.4、初始错误 25%)下,排序不变:F ≥ E > D ≈ B > C > A。代码变动 ×2 时 E 的错答从 5.0 升到 8.6,F 只升到 4.0,代码锚定在高变动下价值更大。

## 6. 最终架构

```
┌─ 使用者机器(Claude Code)──────────────┐        ┌─ 知识库 server ───────────────┐
│ user-scope skill:kb-search / kb-note   │        │ 条目:key、值、source 路径:行区间 │
│ script:                                │ 查询    │       、写入时 commit 与区间 hash │
│  · 查询 → 返回结果 + 状态旗标           │ ─────▶ │ 检索:FTS5/BM25,不用时间衰减     │
│  · 本机比对区间 hash → 标「可能过期」    │ ◀───── │ 同 key 覆盖,子 key 追加          │
│  · 候选回写的暂存箱 outbox(只在本机)    │        │ 已被确认 ≥2 次的条目:单人覆盖     │
│  · push 前后检查「你改到的条目」         │ 写入    │   先标 disputed,不直接改        │
│ 私人笔记:~/.claude/kb-private(不上传)   │ ─────▶ │ 旗标:refuted / disputed / 确认数 │
│ 你按 y 才送出,默认跳过                  │        │ 版本历史、可还原、可删除(墓碑)    │
└────────────────────────────────────────┘        └──────────────────────────────┘
                                                      ▲
                                      repo CI(可选):对可机械抽取的事实,
                                      合并时与夜间自动把缓存值对齐成代码里的值
```

### server 做的事
1. **存**:key(模块 + 主题)、值、`source path:行区间`、写入时的区间 hash 与 commit、时间戳、确认数、旗标、版本历史。**不存作者,不存对话原文,不存程序代码,只存事实**。
2. **检索**:BM25。时间只在「同一个 key 有多条」时选较新的,**不要拿时间当排序权重**(拿掉会让正确率从 95.8 掉到 90.2)。
3. **写入**:同 key 覆盖;不同子 key 追加;立即生效(不要审核关卡,**审核延迟 2 天比不审核更糟**)。审核用事后的版本历史加还原。
4. **冲突处理**:已被验证 ≥2 次的条目,别人想改成不同值时,先标 disputed、旧值保留,**第二个人核对后才真正改**。改代码的人(push 时带区间 hash 变化)的写入,视为权威,直接生效。
5. **回传的旗标**:refuted、disputed、确认数。过期由本机比对。
6. **不做**:判断对错、去重、合并文字。

### 本机 skill 与 script 做的事
1. **读**:`kb search` 在你动某区域前自动查,免费、不要求回写。每条结果带状态。
2. **过期比对在本机做**:script 对条目的 `source:行区间` 算当前 hash,与条目里的比较,不同就显示「⚠ 可能过期」。**server 不需要看到你的代码**。
3. **候选回写,不自动送出**。下面四种情况会产生一条候选,放进 outbox:
   - KB 答案与你刚读到的代码不同。
   - KB 查不到,你自己读代码找到了。
   - 照 KB 的答案做,测试失败。
   - 被标「可能过期」的条目,你核对完了。
4. **push 前后**:script 检查你的 diff 动到哪些条目的区间,列成一次清单(最划算的触发点)。
5. **什么时候问**:任务结束时一次,最多 3 条,一行一条,按键 `y 更新团队 / p 只存给自己 / s 跳过 / n 这条别再问`。没有定时提醒。
6. **送出前的机械过滤**:密钥格式、黑名单路径、`#private` 标记;没有 `source:行区间` 的内容不能升级到团队,只能留在私人区。
7. **匿名信号**:测试失败后可送出 `refute(条目 id)`,只含条目 id 与结果,不含人名与内容。`kb sent` 看得到所有送出过的东西,`kb forget <id>` 可撤回。

### 为什么这样让人安心
- 读不要求回写;写由你按键;跳过不留记录。
- 不录对话,不读私人笔记,server 看不到代码。
- 你能随时看到「送出了什么」并撤回。
- 对参与度宽容:有 20% 的人不写几乎没有损失。

### token 成本
候选的内容由 script 用规则预先填好(key、值、来源),Claude 只看到几行提示。我粗估每条几十到一百多 token,**没有实测**。没有定时提醒,所以没有固定的 token 开销。

## 7. 上线与验证

1. 先做:检索去掉时间衰减、server 的 key / 值 / 路径 / hash / 旗标、本机的 search 与过期比对。这三项最便宜,效果最大。
2. 再做:push 时的清单提示(T1),以及核对时的候选提示。
3. 再做:测试失败回传 refute,以及 disputed 保护。
4. 有常量或配置类知识再做:代码锚定(CI)。
5. **小范围真人试用时量**:提示的接受率与跳过率;每周抽 20 条条目对代码核对,算「错且没警示」;使用者是否觉得被打扰(问卷即可)。

## 8. 限制

- **人是规则模拟,不是 LLM**。回写意愿、拒绝比例、测试抓漏率、误读率、代码锚定覆盖(60%)都是假设值。看排序与机制效果,不要把绝对数字当预测。
- 只跑 6 个种子;小于约 1 个百分点的差异当噪声。
- 代码是合成的常量与推导值。设计原因、流程类知识更难判对错,也不能锚定。
- 这次 A、B 的参数(PR 延迟 2 天、30% 拒绝录制、噪音 ×4)是依现有产品的做法估计的,我没有实际量过那些产品。
- 提示的 token 成本和「使用者是否觉得被打扰」都没有实测,需要真人试用。
