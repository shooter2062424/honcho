# 知識庫 POC 報告：Honcho 與 ai-memory 能否把大家共同維護的知識導向「真相」

本報告回答兩個問題：

1. 多人一起維護知識，內容有對、有錯、有閒聊，系統能不能往 truth 收斂。
2. 大家高頻率使用時，會不會卡頓。

另外依你的補充，加測了「圖片」這類知識來源。

所有程式與原始結果在 `poc/knowledge-db/`，可重跑。

---

## 1. 先講結論

1. **兩個系統都不會自己走向真相。** 它們都是「儲存加檢索」，不是「驗證」。錯誤、過時、閒聊的內容都會被存起來，也都會被檢索出來。
2. **差別在於它們替你保留了什麼。** 能不能收斂，取決於你在它上面加的「裁決層」，而裁決層需要每一筆主張都有「誰說的、什麼時候說的、順序」。
   - ai-memory 保留得多：頁面、版本歷史、每行有貢獻者。
   - Honcho 保留得少：精確重複的句子會被合併，順序與重複次數丟失。
3. **加上簡單的裁決層後，準確率明顯上升。** 在完整帳本上，「依信譽加權投票，再讓可信貢獻者的最新主張勝出」把準確率從 0.60 到 0.65 提到 0.89 到 0.90，對「事實已經改變」的題目，原生 vote 在 Honcho、m2、m3 都接近 0，裁決層提到 0.69 到 0.75。
4. **高頻使用的卡頓：ai-memory 的寫入路徑是瓶頸，Honcho 的瓶頸是背景延遲。**
   - ai-memory（MCP 寫頁路徑）在本沙箱約 4 次寫入每秒，一旦有寫入，讀取排在寫入後面，p50 讀取延遲 3 到 7 秒。
   - Honcho 的 API 在同樣負載下維持亞秒到 2 秒，但從寫入到「搜得到」要等 10 到 60 秒，取決於 LLM 延遲與積壓。
5. **圖片兩者都不原生支援。** 要靠「OCR 或視覺模型轉文字，再帶圖片雜湊」的旁路。畫質差時，OCR 本身會丟失事實。
6. **這修正了我先前的推薦。** 如果你要的是「團隊共同維護的知識庫」，而不是「為每個人建模」，ai-memory 的資料模型比 Honcho 貼題。完整理由見第 8 節。

## 2. 方法與限制（先看這節再看數字）

### 2.1 受測系統

| 系統 | 版本 | 設定 |
|---|---|---|
| Honcho | 3.5.0（本 repo） | Postgres 16 加 pgvector 0.6，API 一個行程，deriver 4 個 worker，無認證，`DERIVER_FLUSH_ENABLED=true`，dream 關閉 |
| ai-memory | 3.3.0（從原始碼編譯） | `serve --transport http`，無認證，只開 FTS 與實體與圖與觀察串流，**沒有設定 embedding 與 LLM** |

ai-memory 的寫入方式分三種，因為它沒有單一「團隊知識庫」的標準用法：

| 模式 | 做法 | 對應的真實用法 |
|---|---|---|
| m1 | 一個事實一頁，後寫覆蓋前寫 | 把它當 wiki，最新版本勝出 |
| m2 | 一個事實一頁，每筆主張附加一行 `[貢獻者] 內容` | 保留所有說法 |
| m3 | 每則訊息各自一頁 | 全部倒進去，與 Honcho 的餵法最接近 |

m1 與 m2 假設有一個聰明的 agent 把閒聊挑掉、把主張路由到正確的頁面。**這個分流與過濾是 ai-memory 本身沒有的，是我替它補的，對它有利。**

### 2.2 模擬的團隊

- 80 個事實：20 個服務乘上 4 個屬性（port、timeout、owner、region）。
- 12 個人：4 個專家（正確率 95%）、5 個一般人（75%）、3 個搗亂者（25%）。
- 三個階段，每階段 800 則訊息，共 2400 則。
- 第二與第三階段開頭，各有 20% 的事實改變，舊說法變成過時。
- 12 個事實有「迷思」：一般人有 60% 機率重複同一個錯誤值。
- 約 30% 是純閒聊，約 15% 的事實訊息尾巴黏著閒聊。
- 專家會對改變的事實發出一次「Correction」，搗亂者有時也發一條錯的 Correction。
- 全部主張裡有 36% 到 40% 是錯的。

### 2.3 必須知道的人為因素

這些都會影響你怎麼解讀數字。

| 因素 | 影響 |
|---|---|
| **Honcho 的 LLM 是我寫的替身** | 它是「不辨真偽但抽取完美」的抽取器：作者說的每個三字以上句子都變成結論，對的錯的閒聊都抽。真 LLM 會有自己的誤差，也可能順手過濾一些閒聊。所以這裡量到的是**系統架構**對主張的處理，不是 LLM 品質 |
| **Honcho 的 embedding 是詞袋雜湊** | 沒有語意，只有字面重疊。對模板化語料合理，但不代表真 embedding 的行為 |
| **Dreamer 沒有評估** | Honcho 的做夢需要真 LLM 呼叫工具，替身做不到，所以演繹與歸納層、`delete_observations` 整併都沒測。這是 Honcho 的主要去重與修正機制，**缺這塊對它不利** |
| **ai-memory 沒開 embedding、LLM、dream、consolidation** | 它的語意檢索、LLM 整併、信念強度權重（預設關）都沒測，只測了零 LLM 的預設路徑 |
| **只測了 ai-memory 的 MCP 寫頁路徑** | 它的文件說 hooks 路徑有較高吞吐（自述約 700 次每秒的 SQLite 寫入上限），我沒有測 |
| **沙箱是 4 核心，所有東西同一台** | Postgres、API、deriver、替身 provider、ai-memory、壓測客戶端共用 CPU。**絕對數字只能看量級，要看相對關係** |
| **壓測客戶端是 Python 執行緒** | 在 64 執行緒時客戶端本身也會貢獻一些延遲 |
| **系統層實驗只跑一個種子** | 裁決層的穩健度另外用 10 個種子驗過（見 4.3），但系統層（含寫入路徑）只有種子 7 |
| **裁決層在看過結果後調整過** | 「可信貢獻者最新主張勝出」是看到第一版結果後才加的。已用 10 個種子檢查沒有過擬合，但仍是事後設計 |

## 3. 實驗一：能不能往真相收斂

評估方式：每階段結束後，對 80 個事實各問一次（Honcho 用語意查詢，ai-memory 用 FTS 查詢），看系統「給的答案」對不對。

三種讀法：

- **top1**：取排名第一的結果。這是一個天真的 agent 會做的事。
- **vote**：在取回的結果中，依權重投票。Honcho 用 `times_derived`，ai-memory m2 用每行一票。
- **曝光（exposed）**：取回的前 10 筆裡，只要有任何一個錯誤值就算。反映 agent 會不會看到矛盾資訊。

### 3.1 原生答案準確率（第 3 階段結束時，80 題）

| 系統 | top1 | vote | 「已改變」題 top1 | 「迷思」題 top1 | 前 10 筆含錯誤值 |
|---|---|---|---|---|---|
| Honcho | 0.175 | 0.713 | 0.125 | 0.083 | 80 / 80 |
| ai-memory m1（後寫覆蓋） | 0.600 | 0.600 | 0.562 | 0.583 | 32 / 80 |
| ai-memory m2（附加） | 0.600 | 0.700 | 0.562 | 0.583 | 80 / 80 |
| ai-memory m3（全倒進去） | 0.375 | 0.662 | 0.000 | 0.333 | 80 / 80 |

> 「已改變」題在第 3 階段只有 16 題，「迷思」題 12 題，樣本小，看量級。

**怎麼讀這張表**

- **Honcho 的 top1 是 0.175，比亂猜還差。** 原因是同一事實的各種說法，向量相似度幾乎一樣，排名取決於細微差異，等於隨機。語意檢索沒有「哪個說法比較可信」的概念。
- **vote 能救回來**，因為 `times_derived` 記錄了「這句話被重複導出幾次」，多數意見通常是對的。但對「已改變」的事實是 0.0，因為舊說法累積的票數壓過新說法。
- **ai-memory m1 看起來最好（0.60）**，但它的準確率等於「最後一個寫入的人是對的機率」，約等於全體主張的正確率，沒有任何收斂力。它的「前 10 筆含錯誤值」只有 32，是因為每個事實只剩一個值，矛盾被抹掉了，不是因為更接近真相。歷史也一起被抹掉（見 3.2）。
- **所有系統的「曝光」都是 80/80（m1 除外）**：agent 一定會同時看到對的與錯的。

### 3.2 帳本保留了什麼

「帳本」指從系統裡讀回所有主張，以及誰說的。

| 系統 | 送進去的主張 | 讀回的主張 | 損失 |
|---|---|---|---|
| ai-memory m3 | 1704 | 1704 | 無 |
| ai-memory m2 | 1704 | 1704 | 無（行內有貢獻者，順序是頁內時間序） |
| Honcho | 1704 | 525 | **精確重複的句子被合併**；順序只剩「首次出現」；`times_derived` 只計跨批次的重複 |
| ai-memory m1 | 1704 | 80 | **被覆蓋的主張消失**（git 有歷史，但不在查詢路徑上） |

Honcho 的合併是它設計的去重機制，優點是省空間，代價是「同一個人重複說同一件事」與「舊說法在新說法之後又被重複」這兩種訊號都丟了。

### 3.3 加上裁決層

我在各系統**讀回的帳本**上跑兩種裁決，不依賴任何模擬器知識：

- **TD（truth discovery）**：反覆估計每位貢獻者的信譽（與當前共識一致的比例），依信譽加權投票，近期主張權重略高。
- **trusted-latest**：TD 之後，若某事實有信譽 0.8 以上的貢獻者說過話，取其中**最新**的一筆。

第 3 階段結束時，80 題的準確率：

| 帳本來源 | 主張數 | TD 全部 | TD 已改變 | trusted-latest 全部 | trusted-latest 已改變 | trusted-latest 迷思 |
|---|---|---|---|---|---|---|
| 完美帳本（上限） | 1704 | 0.863 | 0.312 | **0.887** | **0.688** | 0.833 |
| ai-memory m3 | 1704 | 0.863 | 0.312 | 0.887 | 0.688 | 0.833 |
| ai-memory m2 | 1704 | 0.787 | 0.062 | **0.900** | **0.750** | 0.750 |
| Honcho | 525 | 0.725 | 0.000 | 0.637 | 0.000 | 0.583 |
| ai-memory m1 | 80 | 0.600 | 0.562 | 0.600 | 0.562 | 0.583 |

> ai-memory m2 的 TD 較低，是因為我的 TD 用「帳本全域位置」當時間，而 m2 的行只有頁內順序，沒有時間戳。trusted-latest 只需要事實內順序，所以不受影響。這本身就是一個發現：**帳本要有時間戳。**

**穩健度**：在完美帳本上，用 10 個不同種子重跑，結果（平均，範圍）：

| 方法 | 全部 | 已改變 |
|---|---|---|
| TD | 0.856（0.812 到 0.887） | 0.312（0.125 到 0.500） |
| trusted-latest | **0.926（0.887 到 0.975）** | **0.831（0.625 到 0.938）** |

**怎麼讀**

- 完美帳本下，裁決層把準確率從「不到 0.65」提到 0.89 到 0.93。這說明**收斂是可行的，但要靠裁決層，不是儲存層**。
- Honcho 在這個裁決下反而比原生 vote 差（0.637 對 0.713）。原因是它的帳本丟了順序與重複，「最新」不可信。
- ai-memory m2/m3 的帳本最適合做裁決。
- **0.89 到 0.93 不是 1.0。** 剩下的錯誤主要來自迷思（多數人重複同一個錯值）與剛改變而還沒有可信者確認的事實。**純演算法無法分辨「多數人一致的錯」，這需要外部驗證（人工、測試、權威來源）。**

## 4. 實驗二：高頻使用會不會卡頓

### 4.1 序列寫入（第 3 節實驗中順便量到）

每階段 800 則訊息：

| 系統 | 第 1 階段 | 第 2 階段 | 第 3 階段 | 查詢平均 |
|---|---|---|---|---|
| Honcho（收訊息） | 3.4 秒 | 3.2 秒 | 3.6 秒 | 約 20 毫秒 |
| Honcho（背景處理完成，LLM 延遲 0；含 deriver 輪詢間隔） | 13.0 秒 | 13.5 秒 | 8.5 秒 | |
| ai-memory m1 | 39 秒 | 68 秒 | **93 秒** | 5 到 7 毫秒 |
| ai-memory m2 | 116 秒 | 144 秒 | 174 秒 | 9 到 13 毫秒 |
| ai-memory m3 | 195 秒 | 236 秒 | 269 秒 | 6 到 8 毫秒 |

**ai-memory 的單次寫入隨資料量變慢**：m1 每階段的耗時由 39 秒增到 93 秒，每則寫入從約 49 毫秒變成約 116 毫秒。每次寫頁都會做一次 git checkpoint（回應裡有 `checkpoint` 欄位），這很可能是成長的來源，但我沒有做剖析確認。

### 4.2 併發混合負載（30% 寫、70% 讀，閉環客戶端，30 秒）

| 系統 | 客戶端 | 讀 rps | 讀 p50 | 讀 p99 | 寫 rps | 寫 p50 | 寫 p99 | 錯誤 |
|---|---|---|---|---|---|---|---|---|
| Honcho | 8 | 40.1 | 127 毫秒 | 212 毫秒 | 16.3 | 163 毫秒 | 284 毫秒 | 0 |
| Honcho | 32 | 36.5 | 460 毫秒 | 1.2 秒 | 16.0 | 756 毫秒 | 1.5 秒 | 0 |
| Honcho | 64 | 36.3 | 681 毫秒 | 1.9 秒 | 15.5 | 2.3 秒 | 3.2 秒 | 0 |
| ai-memory m1 | 8 | 11.4 | 225 毫秒 | 1.1 秒 | 4.1 | 1.0 秒 | 2.1 秒 | 0 |
| ai-memory m1 | 32 | 7.9 | **3.3 秒** | 5.5 秒 | 4.0 | 1.4 秒 | 2.8 秒 | 0 |
| ai-memory m1 | 64 | 9.0 | **6.6 秒** | 10.0 秒 | 3.8 | 1.7 秒 | 4.8 秒 | 0 |
| ai-memory m2 | 64 | 8.6 | 7.1 秒 | 11.0 秒 | 3.6 | 1.7 秒 | 5.2 秒 | 0 |
| ai-memory m3 | 64 | 8.3 | 7.1 秒 | 11.3 秒 | 3.6 | 1.6 秒 | 6.0 秒 | 0 |
| Honcho（熱點：全部寫同 5 個主題） | 32 | 35.8 | 475 毫秒 | 1.3 秒 | 15.7 | 809 毫秒 | 1.3 秒 | 0 |
| ai-memory m1（熱點） | 32 | 7.0 | 3.1 秒 | 5.3 秒 | 3.5 | 2.0 秒 | 5.5 秒 | 0 |

（完整表格含 m2/m3 的 8 與 32 客戶端，見 `poc/knowledge-db/results/load.log`。）

**怎麼讀**

- **ai-memory 的總吞吐從 8 個客戶端起就到頂**（約 4 寫每秒、約 9 讀每秒），再加客戶端只是讓排隊更長。**讀取被寫入拖住**：寫入平均要 1 秒以上，且讀取在同一個瓶頸後面排隊。64 個客戶端時，讀取 p50 超過 6 秒，這就是使用者感受到的「卡頓」。
- ai-memory 的**熱點寫入並沒有比分散寫入更糟**，沒有看到衝突錯誤，表示瓶頸不在鎖衝突，更像是每次寫入的固定開銷與單一寫入者。
- **Honcho 的 API 在這個負載下比較平順**，但 64 個客戶端時寫入 p50 已到 2.3 秒，表示它在這台 4 核心機器上也接近飽和（同一台機器還在跑 Postgres 與替身 provider）。
- **兩邊都沒有任何錯誤或資料遺失**（讀寫錯誤數皆為 0）。

> 再次提醒：這是 MCP 寫頁路徑。ai-memory 文件說另有 hooks 路徑吞吐較高，我沒有測。如果你的用法是「agent 的 hooks 自動記錄」而不是「agent 呼叫寫頁工具」，ai-memory 的數字可能好很多。

### 4.3 Honcho 的另一種延遲：寫入到「搜得到」

Honcho 的寫入是非同步的。API 回應很快，但訊息要經過背景抽取才變成可搜尋的結論。我把替身 LLM 設成每次呼叫 800 毫秒，量這段延遲：

| 情境 | 結果 |
|---|---|
| 閒置 60 秒後寫一則，量到搜得到 | **9.4 秒** |
| 先前一次實測（LLM 延遲 0，閒置更久） | 約 26 秒（輪詢退避最長 30 秒） |
| 1 個 session 瞬間灌 1000 則，緊接著寫一則探針 | 探針 **20.4 秒**後可見；全部處理完 43.8 秒 |
| 20 個 session 瞬間灌 3000 則，緊接著寫一則探針 | 探針 **42.4 秒**後可見；全部處理完 61.9 秒；接收端 15.3 秒收完（約 200 則每秒） |

ai-memory 的寫入是同步的：回應回來時，內容已經可以查到。

**重要**：我的設定開了 `DERIVER_FLUSH_ENABLED=true`。**預設是關的**。預設下，一個工作單元要累積 512 token，或最舊的一筆超過 1800 秒，才會被處理。依原始碼，**低流量時最壞要等 30 分鐘才搜得到**。我沒有實測預設值，這是從 `queue_manager.py` 讀出來的。

### 4.4 一個意外發現：向量搜尋在大量近似句下漏掉精確比對

在第一次 5000 則的積壓測試中，我寫入的探針句子（`The port of probeburst is 4242.`）已經存進資料庫，但 Honcho 的語意查詢**一直回傳不到它**，我的腳本因此卡住。

我直接用 SQL 驗證：

| 查詢方式 | 最近的結果（餘弦距離） |
|---|---|
| pgvector HNSW，預設 `ef_search=40` | `svc10` 某句，**0.5955**（探針**不在**前 4 名） |
| 精確掃描 | **探針，0.3258** |
| HNSW，`ef_search=400` | `svc05` 某句，0.5039（探針仍不在前 4 名） |

**也就是說，在 5000 條高度相似的句子裡，HNSW 近似搜尋漏掉了真正最近的那一條。**

**這個結果有保留**：我的詞袋雜湊向量讓大量句子的距離完全相同（0.5955 重複出現），這是一種人造的退化結構，真的 embedding 模型不一定會這樣。但「同一事實的不同取值，句子只差一個 token」在真實的團隊知識庫裡很常見，近似搜尋在這類密集近似簇裡漏掉結果，是值得驗證的風險。

## 5. 實驗三：圖片

### 5.1 原生支援

| 系統 | 傳 PNG | 傳「只有圖片的 PDF」（掃描檔） |
|---|---|---|
| Honcho | **415**，`Unsupported file type: image/png`，支援的只有 PDF、純文字、JSON | **201 成功，但訊息內容是空字串，產生 0 個結論**。沒有任何錯誤或警告 |
| ai-memory | 匯入工具 README 明講：「Images, raw audio/video ... are not supported」，「The original opaque file is never uploaded or stored」 | 同上，README 說「Image-only PDFs need OCR before import」 |

**Honcho 的掃描 PDF 是靜默失敗**，使用者會以為上傳成功。這是需要特別注意的陷阱。

我另外試了把 PNG 做成 base64 資料網址寫進 ai-memory 的頁面：寫得進去，但用文字查詢找不到（它只是一串 base64，沒有任何可檢索的內容）。

### 5.2 旁路：圖片轉文字，帶著圖片雜湊

做法：圖片算 SHA-256，用 OCR 抽出文字，把文字當成一般訊息或頁面寫入，內容前綴 `[img:<雜湊>]`，這樣之後能追溯到原圖。圖片本體要另外放物件儲存，兩個系統都不替你存。

我用 40 張合成圖（每張 3 個事實，共 120 個），分四種畫質，用 Tesseract 做 OCR：

| 畫質 | OCR 後正確還原的事實 | 比例 |
|---|---|---|
| 乾淨 | 27 / 30 | 90% |
| 低解析度 | 24 / 30 | 80% |
| 有雜訊 | 12 / 30 | 40% |
| 旋轉加雜訊 | 6 / 30 | **20%** |

**OCR 失敗的情況，在我的資料裡全部是「解析不出」，沒有產生「讀成錯誤值」的事實（錯誤值數 = 0）。** 這代表圖片的主要風險是**丟失事實**，在這組資料裡不是**注入錯誤**。但這取決於我的模板句子格式（OCR 錯一個字就不符合模式）。真實的截圖與手寫板書，數字被讀錯的情況會出現，這需要你用真實素材驗證。

寫入後，120 個圖片事實：

| | 能查到精確句子 | 能追溯到來源圖片 |
|---|---|---|
| Honcho | 83 | 57 |
| ai-memory（m3 模式） | 94 | 49 |

> 能查到的數字比 OCR 正確數（69）多，是因為同一個事實可能出現在不同張圖裡。能追溯的數字較低，是因為同一事實被多張圖支持時，查詢只會回傳其中一筆。

**Honcho 的 `source_message_ids`（3.5 新增）讓追溯有結構化的路徑**，ai-memory 則要靠行內前綴。

### 5.3 圖片知識的設計建議

1. **圖片進來先轉成「文字加雜湊」**，用視覺模型比 Tesseract 好得多，尤其是圖表與手寫。本 POC 只用了 Tesseract，視覺模型沒有測。
2. **把 OCR 信心當成貢獻者信譽的一部分**：低畫質圖片的主張，裁決層應該給較低權重。
3. **圖片本體放物件儲存**，主張裡只存雜湊。
4. **掃描 PDF 要先偵測**：文字長度為 0 就應該擋下來，不要依賴系統報錯（Honcho 不會報）。

## 6. 發現與解讀

### 6.1 「知識庫」與「使用者建模」是兩個不同的問題

Honcho 的資料模型是「對一個人建立長期理解」：每個 peer 有自己的記憶容器。我為了公平，把全部人的主張都當成同一個 `team` peer 的訊息餵進去。這是**把一個為「建模每個人」設計的系統，拿來當「共同維護的事實庫」用**，是它的非典型用法。

如果改成每個貢獻者各有一個 peer，主張會落在各自的容器裡，**不同人的說法之間完全不會互相比對或收斂**，這是 Honcho 設計上的隔離。我沒有把這個情境做成實驗，這是從資料模型推論的。

ai-memory 的模型本來就是「共用的 wiki」，每頁有版本歷史、取代鏈、證據記錄，並且有「矛盾只標記不解決」的設計。這對共同維護事實庫更貼題。

### 6.2 「閒聊」其實沒那麼糟，真正的問題是「錯」與「舊」

三種雜訊的影響不一樣：

| 雜訊 | 影響 |
|---|---|
| 閒聊 | 佔空間，拉長處理時間，但事實查詢是針對性的，**幾乎不會被閒聊搶走排名**（本 POC 的查詢都帶事實關鍵字）。如果用「最近發生了什麼」這類泛問題，閒聊會污染結果，我沒有測 |
| 錯誤 | 無法靠儲存層分辨，**只能靠裁決層**（多數、信譽） |
| 過時 | 最難。舊說法數量多，新說法數量少，**多數決會輸給過去**。需要「可信貢獻者的最新主張勝出」這類明確的取代規則 |

### 6.3 「已改變」的事實是收斂的主要敵人

所有「只看票數」的方法，在改變的事實上都接近 0。只有「時間加信譽」的規則能救回來（0.31 到 0.69，0.06 到 0.75）。**這與 Honcho 排名不看時間的缺點（我在先前文件中列為高嚴重度）直接呼應，現在有實測支持。**

### 6.4 向量搜尋與「版本衝突」的相互作用

當同一事實的各種取值只差一個 token，**向量相似度無法區分它們**（Honcho 的 top1 只有 0.175），而且在大量近似句下近似搜尋還可能漏掉結果（4.4）。FTS 搭配每個事實一頁的結構（ai-memory m1/m2），反而讓「同一事實的所有說法在同一頁」，不依賴相似度排序。

## 7. 這個 POC 沒有回答的問題

| 沒回答的問題 | 原因 |
|---|---|
| 真 LLM 抽取後的品質 | 沒有 API 金鑰，用了替身。真 LLM 可能自己過濾部分閒聊與明顯錯誤，也可能引入改寫造成的新誤差 |
| Honcho 的 Dreamer 能否整併衝突 | 需要真 LLM。這是 Honcho 最主要的去矛盾機制，**很可能讓 Honcho 的結果比本報告好** |
| ai-memory 的 embedding、LLM 整併、信念強度權重、做夢 | 都沒開 |
| 真實 embedding 下的檢索品質 | 用了詞袋雜湊 |
| ai-memory 的 hooks 高吞吐路徑 | 沒測 |
| 跨使用者的存取隔離 | 兩邊都關了認證，只測了功能不測授權 |
| 多機器、網路延遲 | 全部在 localhost |
| Honcho 預設設定（`FLUSH` 關）下的延遲 | 只從原始碼推論 |
| 長期（週、月）的行為 | 只模擬了三個階段 |
| 真實使用者的錯誤分佈 | 36% 到 40% 的錯誤率是我設的，可能比真實團隊高 |

## 8. 建議

### 8.1 對先前推薦的修正

我先前推薦 Honcho，理由是跨 session、多視角、可稽核。那份推薦的假設是「為每個人建立長期理解」。

**如果你的需求是「大家一起維護同一份知識，並往真相前進」，這個 POC 的證據是：**

- ai-memory 的資料模型（共用頁面、版本、取代、證據、貢獻者）比較貼題，而且它的帳本最適合做裁決。
- Honcho 的語意檢索在同一事實的多個版本之間無法排序，去重還會丟掉裁決需要的順序與重複次數。
- 但 ai-memory 的 MCP 寫頁路徑在高併發下有明顯的卡頓。它的星數約 14.7k，比 Honcho 多，但我沒有評估兩者的維護團隊規模與穩定度。

**如果你的需求是「為每個使用者建立長期理解，順便能跨裝置存取」，先前的推薦仍然成立。**

### 8.2 無論選哪個，你都需要一個裁決層

POC 顯示的最小可行設計：

1. **每一筆主張記錄：貢獻者、時間戳、事實鍵、取值、來源**（文字訊息、圖片雜湊、文件）。
2. **事實鍵標準化**：「某事實的當前答案」是一個明確的鍵，不是靠相似度找。
3. **信譽**：依與共識的一致程度迭代估計，不要寫死。
4. **取代規則**：可信貢獻者的最新主張勝出（本 POC 實測 0.89 到 0.93）。
5. **爭議佇列**：當可信貢獻者彼此矛盾，或多數與可信者不一致（迷思），**送人工或自動驗證**，不要硬選。
6. **保留歷史**，不覆蓋。
7. **圖片**走旁路，並把 OCR 信心併入信譽。

這個裁決層可以建在兩個系統之上，工作量不大。本 POC 的 `td_final.py` 是一個可運作的原型（約 40 行）。

### 8.3 如果一定要在兩者中選一個作為底座

| 你最在乎 | 建議 |
|---|---|
| 共同維護事實，需要完整歷史與人看得懂的內容 | **ai-memory**，用 m2 或 m3 的模式，並確認你的寫入路徑（hooks 或 MCP）撐得住 |
| 高併發、多使用者、有權限分級與 JWT、有 SDK | **Honcho**，但要自己補順序與重複次數（例如把貢獻者、時間戳放進訊息 metadata，查詢後自己裁決），並評估 AGPL |
| 兩者都要 | 用 Honcho 做「每個人」的記憶，用另一層（可以是 ai-memory）做「共同事實」，中間由裁決層連接 |

### 8.4 下一步（會改變結論的實驗）

1. 用真 LLM 重跑 Honcho，開啟 Dreamer，看它的去矛盾能不能追上裁決層。
2. 用 ai-memory 的 hooks 路徑重跑壓測。
3. 用你自己的真實資料取代模擬（最重要）。
4. 開啟認證，驗證 A 用戶的金鑰讀不到 B 用戶的資料。
5. 圖片改用視覺模型。

## 9. 如何重跑

```bash
cd poc/knowledge-db
# 需要：Postgres 16 加 pgvector（埠 5433）、ai-memory 二進位、Honcho 的 uv 環境
source honcho_env.sh
bash start_provider.sh 0          # 替身 LLM（參數是每次呼叫的延遲毫秒）
python3 run_truth.py 7            # 實驗一
python3 td_final.py               # 裁決層（含完美帳本與 10 種子驗證請見報告）
./load_matrix.sh                  # 實驗二：併發負載
python3 run_backlog.py 20 3000 0  # 實驗二：Honcho 積壓
uv run --no-project --with pillow python run_image.py   # 實驗三
```

腳本中的路徑是 `/home/user/poc/...`，在別的機器要自己改。原始結果在 `results/`。
